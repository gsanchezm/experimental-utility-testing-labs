## Purpose

Records, neutrally and descriptively, what bounds the audit of the system under test (SUT) SUT-04: what the ecosystem intentionally does not cover, what the auditor could not verify and why, environment constraints, and environment considerations. Entries are cross-referenced from audit.md (structural_scope_note column and section 6) and from evidence.csv notes. Nothing here is a score, a finding, or a ranking input.

Intentionally narrow scope is not a penalty. An ecosystem that deliberately does not cover a modality is described here in neutral terms; the corresponding row in audit.md section 3 carries a structural_scope_note, the score remains the rubric score (Score 0 for a structurally absent surface; no N/A level), and the capability rubric (protocol/capability-rubric-v1.md) is applied unchanged. Experimental Breadth and Modality Depth answer different questions (protocol/study-design-v1.md, section 11).

## Scope limitations of the ecosystem (intentional)

- Restful Booker Platform is documented in manifests/sut-manifest.yaml as a "Web/API specialist baseline." At the pinned commit it structurally has no Android and no iOS surface: no Android or iOS project files exist anywhere in the repository tree (build.gradle, AndroidManifest.xml, *.xcodeproj, Podfile — all searched, none found; evidence_id SUT04-EV-0011, SUT04-EV-0013), and docker-compose.yml defines only the seven web/API services. This is intentional narrow scope, not a deficiency (AGENT-INSTRUCTIONS.md, rule 11; protocol/study-design-v1.md, section 11, rules 1 and 3). Android Native and iOS Native are scored 0 with structural_scope_note NO_MOBILE_SURFACE in audit.md section 3.
- No locale/market-selection surface exists in the evaluated version (evidence_id SUT04-EV-0025, SUT04-EV-0026); the only locale-related code fixes date formatting to a single hardcoded locale (en-GB). Localization / i18n is scored 0 with structural_scope_note OTHER_STRUCTURAL_REASON.

## Evaluation limitations (what the auditor could not verify and why)

- **No EXECUTION_VERIFIED evidence was produced in this audit.** Under the Evidence collection order (frozen auditor prompt, step 4), execution verification is reserved for a specific unresolved claim that documentation and source cannot together settle. Every candidate Score 3 in this audit was already fully resolvable from DOCUMENTED and SOURCE_VERIFIED evidence at the pinned commit (both web and api are open source and fully readable), so no execution step was needed to confirm or refute a mechanism. Running the SUT locally would additionally have required JDK 26, Maven 3.9.14, Node 24.14.1/NPM 11.11.0, and Docker (docker-compose.yml), none of which were exercised. The public instance (`http://www.automationintesting.online`) carries an explicit `HOSTED_MAPPING_UNVERIFIED` caveat in manifests/sut-manifest.yaml — its correspondence to the pinned commit `d36bd3f8647a091d406e53bad463c5e3e5d2ece1` is not independently verified — and, separately, E01 prohibits any state-changing execution against a PUBLIC_HOSTED instance (protocol/study-design-v1.md, section 10.2), so it could not in any case have served as EXECUTION_VERIFIED evidence for the API/Web state-seeding or reset mechanisms described in this audit. Consequently: `environment_types_used` (audit.md section 1) is empty, and `controlled_instance_available` is recorded as `null` — not inferred as `true` from the mere presence of docker-compose.yml and build_locally.sh, because local deployability is not itself evidence (protocol/capability-rubric-v1.md, "Decision procedure," constraints) and protocol/study-design-v1.md, section 10.5 requires this fact to be verified by execution, not inferred.
  - What a future controlled (SELF_HOSTED or LOCAL) run from this exact pinned commit would additionally settle: (a) that the documented HTTP endpoints behave exactly as the source predicts at runtime; (b) whether the public hosted deployment's observable behavior matches the pinned commit (resolving the HOSTED_MAPPING_UNVERIFIED caveat, out of this audit's scope); (c) the Security Testing interpretive question recorded in unresolved.md (SUT-04-U01), by directly querying the H2 ACCOUNTS table (`dbServer=true`) to observe the plaintext-password condition at runtime rather than by source inspection alone.
- The evidence ceiling described in protocol/evidence-rules-v1.md, section "Evidence ceiling" (SOURCE_VERIFIED unobtainable for a closed-source or hosted-only component) does not apply here in the strict sense: both the web and api components are open source and were fully readable at the pinned commit. The limiting factor throughout this audit was the auditor's choice not to execute (per the Evidence collection order), not an inability to obtain source.

## Environment limitations

- **Tooling reliability.** In this operator's environment, `git` and `find` are wrapped by a token-optimizing shell hook (`rtk`) that intermittently reformatted or mangled command output. Concretely: immediately after `git checkout d36bd3f8647a091d406e53bad463c5e3e5d2ece1` correctly reported "HEAD is now at d36bd3f ...", a subsequent `git log -1 --format="%H %ci"` printed a different SHA (`964c1ac9...`, an ancestor merge-source commit, not the checked-out HEAD). Commit identity was therefore confirmed authoritatively with `git rev-parse HEAD` (which returned `d36bd3f8647a091d406e53bad463c5e3e5d2ece1`, matching the pin) rather than with `git log`, and no fact in this audit rests on `git log` output. `find` also rejected some compound predicates issued through the wrapper; searches were re-run as separate single-predicate `find` invocations where this occurred (e.g. the Android/iOS mobile-artifact searches, evidence_id SUT04-EV-0011, SUT04-EV-0013). No other tooling limitation was encountered, and no evidence record in evidence.csv rests on unverified tool output.
- The read-only source workspace `../e01-sut-sources/SUT-04-restful-booker/` did not exist at the start of this audit. It was created fresh as a sibling of the audit worktree (outside this repository) per the auditor prompt's Source workspace requirements and the operational launch instructions, cloned from `https://github.com/mwinteringham/restful-booker-platform`, and checked out at exactly `d36bd3f8647a091d406e53bad463c5e3e5d2ece1`. It was never moved to a different commit, branch, or release during this audit.

## Environment considerations

- `environment_types_used`: none (no EXECUTION_VERIFIED evidence was produced; see "Evaluation limitations," above).
- `controlled_instance_available`: `null` (not verified by execution in this audit; see "Evaluation limitations," above). Both the web and api surfaces are open source and documented as buildable via `docker-compose.yml` and `build_locally.sh`, which is itself a DOCUMENTED fact (evidence_id SUT04-EV-0001) — it is not, by itself, the execution-based verification that protocol/study-design-v1.md, section 10.5 requires before this field may be set to `true`.
- **Provenance note (not a capability finding).** manifests/sut-manifest.yaml records the pinned commit `d36bd3f8647a091d406e53bad463c5e3e5d2ece1` (default branch `trunk`) alongside release tag `2.2`, whose own target commit (`60865403c827cb880187c71d7ad03c951e8d4f2c`, per manifests/e01-source-provenance.yaml) is a different, earlier commit. This is not a discrepancy: `git merge-base --is-ancestor 60865403c827cb880187c71d7ad03c951e8d4f2c d36bd3f8647a091d406e53bad463c5e3e5d2ece1` confirmed the release-tagged commit is an ancestor of the pinned commit — i.e., the pinned commit is a later point on the same `trunk` history than the tagged release. Release 2.2 carries no downloadable assets (it is a source/version tag, per the manifest's own note), so the trunk-HEAD commit pin is the primary, and only, provenance this audit evaluated; `assets/package.json` at the pinned commit also carries `"version": "2.2"`, consistent with (though not proof of) the 2.2 lineage. This is disclosed as a mapping note, not escalated to unresolved.md, because it does not affect any score in this audit.
- The hosted endpoint pinned for the web component (`http://www.automationintesting.online`) was not accessed and was not used as evidence anywhere in this audit; its exact correspondence to the pinned commit remains unverified (`HOSTED_MAPPING_UNVERIFIED`, per manifests/sut-manifest.yaml's own note). This audit relies exclusively on DOCUMENTED and SOURCE_VERIFIED evidence from the pinned-commit source tree.
