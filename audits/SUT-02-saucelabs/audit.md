## 4. Cross-cutting properties

Descriptive only; no property is scored (protocol/cross-cutting-properties-v1.md).

### State Controllability

Description (descriptive only, no score): All three surfaces let the experimenter land directly in a defined application state via a fixed, documented-in-app test account rather than replaying a full end-user path: web's six VALID_USERNAMES (SUT02-EV-0001), android's alice@example.com / visual@example.com (SUT02-EV-0007), and ios's visual@example.com (SUT02-EV-0017) each select a distinct, deterministic app condition (locked-out, visual-fault, performance-glitch, standard) at login. None of the three components expose an API-based seeding mechanism (SUT02-EV-0004/0005/0006): the only state-establishment channel found is the login form itself (username selection) plus, on ios, the OS-level locale launch argument (SUT02-EV-0020) for the localization condition. No deep-link-into-a-prepared-state mechanism was found on android or ios (no `<data android:scheme=…>` intent filter; no `CFBundleURLTypes`/associated-domain entry in Info.plist).
Evidence refs (evidence_id): SUT02-EV-0001, SUT02-EV-0007, SUT02-EV-0009, SUT02-EV-0017, SUT02-EV-0020

### Resetability

Description (descriptive only, no score): All three surfaces ship an explicit, source-verified "Reset App State" action plus a separate "Logout" action: web (DrawerMenu.jsx, SUT02-EV-0002), android (MainActivity.java, SUT02-EV-0008), ios (MenuViewController.swift, SUT02-EV-0009). Scope differs slightly: web's reset clears only the shopping cart (ShoppingCart.resetCart()) and logout separately clears the session cookie; android's and ios's reset clears cart plus, on ios, shipping/billing/card form fields, and each also has a separate logout. No mechanism resets android's ambient DeviceVitalsDemo memory-churn timer (SUT02-EV-0012), which runs from app process start regardless of login/reset state. No server-side state exists to reset on any surface, since no business-data API was found (SUT02-EV-0004/0005/0006).
Evidence refs (evidence_id): SUT02-EV-0002, SUT02-EV-0008, SUT02-EV-0009, SUT02-EV-0012

### Determinism

Description (descriptive only, no score):
- deterministic: the locked-out/error/problem/visual/performance-glitch account branches on web (SUT02-EV-0001, SUT02-EV-0003, SUT02-EV-0011, SUT02-EV-0015), android's locked-out and visual image-substitution branches (SUT02-EV-0007, SUT02-EV-0016), ios's visual presentation branch (SUT02-EV-0017), and all three Reset App State / Logout actions (SUT02-EV-0002, SUT02-EV-0008, SUT02-EV-0009) produce the same defined outcome for the same account/action on every run.
- stochastic: on all three surfaces, the same visual_user / visual@example.com account that drives the deterministic image/CSS perturbation also randomizes a displayed price on every render: web's `randomPrice()` (`Math.random()`, Inventory.jsx line 122, SUT02-EV-0015), android's `Random.nextDouble()` (generateVisualChanges in ProductCatalogViewModel.java, SUT02-EV-0016), and ios's `Double.random(in: 1...99)` (CatalogViewController.swift line 189, SUT02-EV-0017). Each is explicitly excluded from its record's expected_behavior and from the Visual Testing Score-3 rationale.
- time-dependent: android's DeviceVitalsDemo runs an ambient, unconditional memory-allocation/release TimerTask (1 MB every 500 ms, up to 32 MB) from app launch, with no activation control (SUT02-EV-0012); this is recorded as a potential confound for any future performance measurement on the android surface, not as SUT-02 capability evidence.
- external dependency: android's telemetry pattern also performs outbound HTTP calls to a Google-hosted JS asset and to a hosted `my-demo-app.net` endpoint (SUT02-EV-0005) whose availability the study does not control; web's Backtrace error-reporting call (src/index.jsx) is the same kind of vendor external dependency, observed but not scored.
Evidence refs (evidence_id): SUT02-EV-0001, SUT02-EV-0002, SUT02-EV-0003, SUT02-EV-0005, SUT02-EV-0007, SUT02-EV-0008, SUT02-EV-0009, SUT02-EV-0011, SUT02-EV-0012, SUT02-EV-0015, SUT02-EV-0016, SUT02-EV-0017

### Observability

Description (descriptive only, no score): No health, diagnostic, or OpenAPI/Swagger-described endpoint was found on any surface (consistent with the absence of a business-data API, SUT02-EV-0004/0005/0006). Observability is UI-level only: each fault condition (locked-out, error, visual, performance-glitch) renders a fixed, distinguishable observable signal — a specific error string, a CSS class, an image substitution, or a fixed added delay — that a testing tool can detect from the rendered page/screen without a dedicated introspection channel. android's Network.java reads response headers/bytes for its outbound calls (SUT02-EV-0005) but discards them (no logging, no UI surfacing), so that channel offers no observability to an external experimenter. No stable, documented entity/session identifiers (comparable to a request ID or order ID) were found in any of the three trees during this audit.
Evidence refs (evidence_id): SUT02-EV-0001, SUT02-EV-0005, SUT02-EV-0011, SUT02-EV-0015

### Automation Affordances

Description (descriptive only, no score): web ships explicit `data-test` attributes across interactive elements (e.g. `data-test="login-container"`, `data-test="login-credentials"` in Login.jsx, and `testId` props threaded into InputError.jsx/SubmitButton.jsx), a stable, documented-in-source automation hook (SUT02-EV-0001). This audit did not specifically search the android and ios trees for an equivalent stable identifier convention (`android:contentDescription` / Espresso resource-id patterns; `accessibilityIdentifier`); their presence or absence is not asserted here and is recorded as a gap in limitations.md rather than guessed.
Evidence refs (evidence_id): SUT02-EV-0001

### Cross-platform Scenario Parity

Description (descriptive only, no score): "Reset App State" + "Logout" exist with full parity across web, android, and ios (SUT02-EV-0002, SUT02-EV-0008, SUT02-EV-0009): same business intent (return to a known clean state), same precondition (logged in), same observable outcome (confirmation message, cart cleared). A "visual fault" test-account scenario also has full parity across all three (SUT02-EV-0015, SUT02-EV-0016, SUT02-EV-0017). A "locked-out account" scenario has only partial parity: present and enforced on web (locked_out_user, SUT02-EV-0001) and android (alice@example.com, SUT02-EV-0007), but the identically-named ios account (alice@example.com, shown as a prefill in Authentication.storyboard) is not enforced by the pinned ios LoginViewController (SUT02-EV-0010) — a documentation-vs-implementation gap, not a parity match. Localization has no parity: shipped only on ios (SUT02-EV-0020), structurally absent on android (only base res/values/, no locale variants) and web (no i18n resources) (SUT02-EV-0021). The business-data API surface is absent identically on all three (SUT02-EV-0004/0005/0006), so no parity question arises there.
Evidence refs (evidence_id): SUT02-EV-0002, SUT02-EV-0007, SUT02-EV-0008, SUT02-EV-0009, SUT02-EV-0010, SUT02-EV-0015, SUT02-EV-0016, SUT02-EV-0017, SUT02-EV-0020, SUT02-EV-0021

### Cross-layer State Continuity

Description (descriptive only, no score): No mechanism was found by which a state established through one layer (web, android, or ios) could be verified through another. This follows directly from the absence of any shared, documented business-data API or backend across the three pinned components (SUT02-EV-0004, SUT02-EV-0005, SUT02-EV-0006): each app's cart/session/account state is confined to its own client-side storage (cookies on web; a singleton/local Room database on android; an in-process Engine singleton on ios), with no shared backend or database observed connecting them at the pinned commits.
Evidence refs (evidence_id): SUT02-EV-0004, SUT02-EV-0005, SUT02-EV-0006

### Functional Complexity

Description (descriptive only, no score): All three surfaces implement a comparable small e-commerce domain: a fixed product catalog (name, price, description, image; web's catalog additionally supports az/za/price-low-high/price-high-low sorting, Sorting.js), a shopping cart (add/remove items, running total), and a multi-step checkout collecting shipping/billing-shaped fields and payment-card-shaped fields (no real payment processing observed on any surface), gated behind the login/test-account mechanism described above. Field-level validation exists on all three (required-field errors on web's Login/CheckOutStepOne; equivalent validation dialogs on android/ios). android and ios additionally ship several demo-only screens outside this core flow (QR code scanner, geolocation, drawing/signature capture, Face ID/biometric login, in-app WebView) that are not tied to any of the nine modalities scored here. This is an inventory, not a ranking; more shipped screens on android/ios than on web is not treated as greater capability.
Evidence refs (evidence_id): SUT02-EV-0001, SUT02-EV-0003, SUT02-EV-0007, SUT02-EV-0009, SUT02-EV-0018
