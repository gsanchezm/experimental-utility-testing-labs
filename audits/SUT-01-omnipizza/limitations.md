## Purpose

Records, neutrally and descriptively, what bounds the audit of the system under test (SUT) SUT-01: what the ecosystem intentionally does not cover, what the auditor could not verify and why, environment constraints, and environment considerations. Entries are cross-referenced from audit.md (structural_scope_note column and section 6) and from evidence.csv notes. Nothing here is a score, a finding, or a ranking input.

Intentionally narrow scope is not a penalty. An ecosystem that deliberately does not cover a modality is described here in neutral terms; the corresponding row in audit.md section 3 carries a structural_scope_note, the score remains the rubric score (Score 0 for a structurally absent surface; no N/A level), and the capability rubric (protocol/capability-rubric-v1.md) is applied unchanged. Experimental Breadth and Modality Depth answer different questions (protocol/study-design-v1.md, section 11).

## Scope limitations of the ecosystem (intentional)

None recorded. All four component surfaces (web, api, android, ios) are present at the pinned versions (audit.md section 2), and no modality was found structurally absent for SUT-01 at this audit (audit.md section 3). Two design-level surface limitations are documented by the ecosystem itself and are recorded here as facts about the evaluated version, not as scope gaps: the iOS mobile build ships as a simulator-only artifact (cannot be installed on a physical device without a distribution certificate, per README.md — SUT01-EV-0013); and the pizza catalog's product images are hardcoded hotlinks to an external host (upload.wikimedia.org), an external dependency the SUT itself does not control.

## Evaluation limitations (what the auditor could not verify and why)

- **Visual Testing is capped by the tie-break rule (audit.md section 3): `confirmed_score = 2`, `provisional_score = 3` retained as an unresolved candidate, `confirmation_state` null.** The two SOURCE_VERIFIED mechanisms found (`problem_user`'s deterministic $0-price/broken-image state, SUT01-EV-0020; the profile-seed endpoint's documented intent to support reproducible snapshots, SUT01-EV-0021) both establish a controlled *data* condition that happens to render visibly differently, not a mechanism the SUT itself exposes as a visual-testing condition as such (contrast Accessibility above, where the same style of data mutation maps onto a named, tool-specific detectable violation). Decision procedure step 3 is undecided at the "is this a mechanism of this modality" level, not merely at the evidence-status level, so the general tie-break rule applies directly (protocol/capability-rubric-v1.md, "Relation to Score 3 confirmation") rather than `confirmation_state = UNCONFIRMED_SCORE_3`. Unresolved verification requirement: a mechanism that establishes a specifically visual perturbation (e.g. a controlled layout, contrast, or rendering condition), or an EXECUTION_VERIFIED screenshot-diff run demonstrating that the existing data condition produces a stable, tool-detectable visual difference against a baseline, would be needed to confirm Score 3. Separately, and not itself determinative of the score either way: the auditor searched `frontend/package.json` and `frontend/cypress` for a screenshot-diff/comparison tool (Percy, pixelmatch, cypress-image-snapshot) at the pinned commit and found none wired in — recorded here as a tooling-absence observation (generic tool absence does not move the rubric score per protocol/capability-rubric-v1.md, "Decision procedure," constraints).
- **No execution was performed.** Every capability claim in audit.md was settled by DOCUMENTED and SOURCE_VERIFIED evidence; SOURCE_VERIFIED evidence was obtainable for every candidate Score-3 mechanism (the ecosystem is fully open-source at both pinned commits), so per protocol/capability-rubric-v1.md, "Score 3 confirmation," execution verification was not required to confirm any cell. Consequently this audit contains zero EXECUTION_VERIFIED records, zero files under `verifications/`, and zero files under `artifacts/`. This is a deliberate application of the "Evidence collection order" (perform execution only to answer a specific unresolved claim), not an access or capability restriction: nothing in this audit needed it.
- **Hosted-endpoint mapping was not independently re-verified.** manifests/sut-manifest.yaml already records the Render endpoints (`omnipizza-frontend.onrender.com`, `omnipizza-backend.onrender.com`) as HOSTED_MAPPING_UNVERIFIED — their exact correspondence to the pinned commits is not independently confirmed. This auditor did not query either endpoint (no execution was performed, per above), so this caveat is unchanged by this audit, not newly introduced by it.
- **`controlled_instance_available` (audit.md section 1) is left unverified (null / TBD).** Confirming it requires actually establishing a controlled instance (SELF_HOSTED/LOCAL for web/api, EMULATED/SIMULATED for android/ios per protocol/study-design-v1.md section 10.5) and observing whether it runs from the pinned version — the auditor did not attempt this (no execution was performed). Source inspection alone (e.g. a `requirements.txt`/`package.json` that appears installable, a documented `docker-compose.yml`/`render.yaml`) is not treated as sufficient to mark this field true, consistent with the rubric's rule that local deployability is never inferred as capability from source alone.
- **The mobile Detox test harness at the pinned android/ios commit is not runnable as configured.** `frontend-mobile/.detoxrc.js` and `frontend-mobile/e2e/experiments/latency_resilience.e2e.js` exist in source, but the `detox` package itself is absent from `frontend-mobile/package.json` and `frontend-mobile/pnpm-lock.yaml` at this exact commit (checked; zero matches for "detox" in the lockfile). This does not change any modality score — the testID selectors the spec exercises (`screen-login`, `input-username`, `btn-login`, etc.) were independently source-verified as present in the actual screen components (SUT01-EV-0011) — but it means this specific pre-existing test file could not have been run as-is at this commit without first adding the missing dependency, and the auditor did not attempt to run it.
- **The `security_glitch_user` seeded-payload mechanism was checked only at the API layer.** The auditor confirmed the backend returns the unsanitized payload verbatim via `GET /api/users/me/profile` (SOURCE_VERIFIED) and confirmed the web client contains no `dangerouslySetInnerHTML` call (so React's default JSX escaping applies to profile fields as currently rendered) — meaning this specific mechanism was not verified to produce an executing client-side XSS in the web UI. The modality's Score 3 does not depend on this mechanism; it is confirmed independently by the order-ownership IDOR (SUT01-EV-0023). See evidence.csv, SUT01-EV-0024, notes.
- **Cross-platform/cross-layer claims (audit.md section 4) were checked on two scenarios, not exhaustively.** "Seed cart via API then land on Checkout" and "select market at login" were both source-verified across Web and Android/iOS. Other possible scenarios (e.g. profile editing, order cancellation) were not individually re-checked for full three-surface parity.
- **Not every source file in the repository was read.** This audit read the backend routers and core modules in full (`main.py`, `auth.py`, `middleware.py`, `constants.py`, `database.py`, `test_api.py`, and all five files under `backend/routers/`), the frontend files directly relevant to the mechanisms cited in evidence.csv (`store.js`, `Catalog.jsx`, `ProductCard.jsx`, `Login.jsx`, package/config files), and the corresponding mobile screens and navigation/hook files at the pinned android/ios commit. It did not read every frontend feature/hook/component file, the `tests/` Vitest/Schemathesis suites in full, `ATOMIC_WEB_TESTING.md`/`ATOMIC_MOBILE_TESTING.md`/`API_EXAMPLES.md`/`VALIDATION_CHECKLIST.md` in full (only README.md and the source files cited in evidence.csv were read in full; the other markdown documents were not read for this audit and are not cited as DOCUMENTED evidence), or the `documents/` product/design docs. A documentation-vs-implementation contradiction outside the files actually read would not have been found.

No evidence ceiling applies to SUT-01: every component (web, api, android, ios) is open-source at a pinned commit, so SOURCE_VERIFIED was obtainable throughout, and no closed-source or hosted-only component required a lower evidence status by default (protocol/study-design-v1.md, section 10.4).

## Environment limitations

No controlled or uncontrolled environment was used: this audit performed zero execution (see "Evaluation limitations" above). No tooling was installed, no server was started, no emulator/simulator was launched, and no request was made to either Render-hosted endpoint. All findings rest on DOCUMENTED evidence (README.md) and SOURCE_VERIFIED evidence (reading actual application source at the two pinned commits, cloned read-only into `../e01-sut-sources/SUT-01-omnipizza/{web-api,android-ios}/`, outside this repository).

environment_types_used: none (audit.md section 1). `controlled_instance_available`: not verified (see above). No shared PUBLIC_HOSTED instance was touched, so no shared-instance interference or state-visibility concern arose during this audit.
