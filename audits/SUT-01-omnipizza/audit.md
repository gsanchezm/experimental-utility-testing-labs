## 4. Cross-cutting properties

Descriptive only; no property is scored (protocol/cross-cutting-properties-v1.md).

### State Controllability

Description (descriptive only, no score): The evaluated version exposes direct, non-UI state establishment on all three client surfaces through one shared backend API: `POST /api/cart` (replace cart), `PUT`/`DELETE /api/cart/items/{item_id}` (upsert/remove one line), `POST /api/store/market` (set market), `POST /api/profile` (seed editable profile) — all keyed by the caller's login session (JWT `sid`), not by username, so concurrent logins for the same test account do not race on shared state. On the Web client, an auth token pre-set in `localStorage` before load is sufficient to reach any protected route without the login UI. On Android/iOS, `omnipizza://` deep links carry `accessToken`, `market`, `lang`, and `hydrateCart` as direct state-establishment parameters, applied before the target screen renders. What is NOT directly establishable: order history — an order can only be created by a full `POST /api/checkout` call (no dedicated "seed an order" test endpoint was found), so pre-loading a specific order history requires replaying checkout, not a single seed call; and the multi-market pricing/currency table and the seven test-user behaviors are fixed data, not independently configurable per run.
Evidence refs (evidence_id): SUT01-EV-0002, SUT01-EV-0004, SUT01-EV-0006, SUT01-EV-0009, SUT01-EV-0010

### Resetability

Description (descriptive only, no score): `POST /api/session/reset` clears the caller's session cart and market and resets the editable profile to its deterministic empty default, scoped to the caller's own session_id (so it cannot affect a concurrent login under the same test username). This mechanism's scope is explicitly partial: it does not clear order history (orders persist in the backend's in-memory store, keyed by `order_id`, with no per-user "clear my orders" endpoint found in source), and the entire in-memory backend (`InMemoryDB`) resets only on server process restart, which this auditor did not attempt (no controlled instance was established; see limitations.md).
Evidence refs (evidence_id): SUT01-EV-0006

### Determinism

Description (descriptive only, no score):
- deterministic: `performance_glitch_user`'s exact 3.0s API delay (SUT01-EV-0015); `locked_out_user`'s unconditional 403 (SUT01-EV-0007); per-market pricing, tax, and currency conversion (`COUNTRY_CONFIG`, `CURRENCY_RATES`); `problem_user`'s fixed $0.00-price / broken-image state (SUT01-EV-0020); catalog/order calculation formulas (`calculate_order_total`).
- stochastic: `a11y_glitch_user`'s per-call random choice among 3 documented content-mutation modes (SUT01-EV-0018); `error_user`/`security_glitch_user`'s ~50% random checkout failure (SUT01-EV-0025); `security_glitch_user`'s random choice of 1-of-3 seeded profile fields and 1-of-3 XSS-style payloads (SUT01-EV-0024); `GET /api/debug/latency-spike`'s randomized 0.5-5.0s delay (SUT01-EV-0016).
- time-dependent: none found. The auditor searched the reviewed backend source (`main.py`, `routers/*.py`, `database.py`, `middleware.py`, `constants.py`) for clock/date-gated business logic and found none beyond timestamping records (order creation time, `/health`, `/api/version`), which does not gate any business outcome.
- external dependency: pizza catalog images are hardcoded hotlinks to `upload.wikimedia.org` (`constants.py`, `PIZZA_CATALOG`), an external dependency outside the study's or the SUT's own control; `problem_user`'s broken-image state instead points at a fixed non-Wikimedia placeholder URL, itself also external.
Evidence refs (evidence_id): SUT01-EV-0007, SUT01-EV-0015, SUT01-EV-0016, SUT01-EV-0018, SUT01-EV-0020, SUT01-EV-0024, SUT01-EV-0025

### Observability

Description (descriptive only, no score): `GET /health` (status/timestamp/environment), `GET /api/debug/info` (app name/version/environment/order count/test-user list/supported countries), `GET /api/version` (app version, environment, `git_commit` from the Render build, process start time), and `GET /api/debug/metrics` (Prometheus-format counters/histograms for request count and latency) are all present and unauthenticated. Full interactive API documentation is served at `/api/docs` (Swagger UI), `/api/redoc` (ReDoc), and `/api/openapi.json` (raw OpenAPI JSON) for every route. Stable identifiers are used throughout: `order_id` (`ORDER-<8 hex>`), cart `item_id` (`ITEM-<8 hex>`), and the JWT `sid` session claim. All of this covers the API layer; the auditor found no separate diagnostic/observability surface specific to the Android or iOS clients beyond what the shared backend already exposes (mobile clients call the same endpoints).
Evidence refs (evidence_id): SUT01-EV-0029

### Automation Affordances

Description (descriptive only, no score): Web: `data-testid` attributes on effectively every interactive element and many content nodes across the pages reviewed (Catalog, ProductCard, Login market selector, Checkout). Mobile (Android/iOS, shared codebase): `testID`/`accessibilityLabel` on every interactive element of the reviewed screens (Login: `screen-login`, `input-username`, `input-password`, `btn-login`, `btn-market-<code>`, `btn-user-<id>` for all 7 test accounts); these exact testIDs are exercised by an existing Detox-style spec at the pinned commit (`e2e/experiments/latency_resilience.e2e.js`), corroborating they are live selectors, not merely declared. API: full OpenAPI/Swagger schema is itself a machine-readable automation affordance. Consistency: selector naming is consistent in style (kebab-case `data-testid` / `testID`) across the reviewed Web and mobile screens, though the auditor did not exhaustively diff every screen pair for one-to-one selector-name parity. One tooling gap: `.detoxrc.js` and the `e2e/` Detox spec exist in source at the pinned android/ios commit, but the `detox` package itself is absent from `frontend-mobile/package.json` and `pnpm-lock.yaml` at that commit — the spec is not runnable as configured without first adding the dependency (recorded in limitations.md; does not change any modality score).
Evidence refs (evidence_id): SUT01-EV-0003, SUT01-EV-0011, SUT01-EV-0029

### Cross-platform Scenario Parity

Description (descriptive only, no score): Two scenarios were checked for parity across all three client surfaces at their respective pinned commits. (1) "Seed cart via API, then land directly on Checkout already hydrated": present and source-verified on Web (`SUT01-EV-0004`) and on Android/iOS (`SUT01-EV-0030`, shared mobile codebase) — full parity for this scenario. (2) "Select a market at login, before entering the app": present and source-verified on Web (`frontend/src/pages/Login.jsx`, `role="group" aria-label="Select market"`, `data-testid="market-<code>"`) and on Android/iOS (`SUT01-EV-0028`, `LoginScreen.tsx` `MARKETS` selector) — full parity. The auditor did not attempt an exhaustive scenario-by-scenario parity sweep across every screen (e.g. Profile editing, order cancellation) on all three surfaces; these two scenarios are the ones directly source-verified above and are reported as full parity, not as a claim about every possible scenario.
Evidence refs (evidence_id): SUT01-EV-0004, SUT01-EV-0028, SUT01-EV-0030

### Cross-layer State Continuity

Description (descriptive only, no score): Web, Android, and iOS clients are three consumers of one shared backend API and one shared in-memory data store (`backend/database.py`, `InMemoryDB`). API -> Web and API -> Android/iOS are both directly source-verified: state seeded via `POST /api/cart` is read back by the Web Checkout page's `GET /api/cart` on mount (`SUT01-EV-0004`) and, identically, by the mobile Checkout screen's own `GET /api/cart` call (`SUT01-EV-0030`). Web -> API and Android/iOS -> API were not independently executed by this auditor; they follow structurally from the single shared backend (any client-driven checkout ultimately calls the same `POST /api/checkout`, and the resulting order is then readable via `GET /api/orders/{order_id}` from any layer) but this was not observed end-to-end by running the UI, so it is recorded as an architectural inference from source rather than an executed trace.
Evidence refs (evidence_id): SUT01-EV-0004, SUT01-EV-0030

### Functional Complexity

Description (descriptive only, no score): Entities: User (7 fixed test accounts, each with one documented `behavior`), Pizza (12 catalog items across 4 categories: popular/veggie/meat/sides-unused), Cart (session-scoped line items with size and toppings), Order (`pending`/`cancelled` status, owned by a username), Profile (editable name/address/phone/notes/birthday), Market (5 countries, each with its own currency, required/optional checkout fields, tax rate, and tip field name). Operations: login, browse/search/filter catalog, customize a pizza (size upcharge + per-topping upcharge, both currency-converted), add/edit/remove cart lines, checkout (country-specific required-field validation), cancel a pending order (`409` if not pending), edit profile. Rules: per-market required checkout fields enforced server-side (`COUNTRY_CONFIG`); order total = subtotal + delivery_fee + tax + tip, all currency-converted and rounded per market's `decimal_places`; order visibility/cancellation restricted to the owning username except for the deliberate `security_glitch_user` bypass (`SUT01-EV-0023`); order cancellation is a one-way `pending -> cancelled` transition only. This is an inventory, not a ranking; the auditor draws no conclusion from it about relative complexity versus any other ecosystem.
Evidence refs (evidence_id): SUT01-EV-0007, SUT01-EV-0020, SUT01-EV-0023, SUT01-EV-0027
