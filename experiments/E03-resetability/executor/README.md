## 1. What the implementation does, and what it never does

For one condition and one attempt it: reads the instance interface (`instance.json`, section 6); performs the precondition and the establishment of the altered (target) state, recorded and never counted; verifies the altered state before the reset, recorded and never counted; performs the reset-side Required Actions in order, each with its per-action outcome; evaluates the post-reset oracle predicate; writes the bundle (section 7) and the run manifest last.

It never modifies, patches, or configures a SUT (AGENT-INSTRUCTIONS.md, rule 3); never retries a failed action that this document does not predeclare (none is predeclared, section 3); never runs against a PUBLIC_HOSTED instance; never writes under `raw-data/` outside a measured workflow run; never reads another SUT's outputs (protocol/agent-governance-v3.md, Section 3.5).

## 3. Counting and recording conventions (protocol/setup-effort-v2.md)

1. Only Required Actions — reset enter `actions[]`: the operations from the declared target state back to the declared starting state (Section 3). The precondition (authentication), the establishment, and the pre-reset verification are recorded in `precondition.json` and never enter `actions[]` (Section 3; Section 5, rule 6).
2. Every experimenter-initiated operation with an observable effect performed after the target state is an action (Section 5, rules 1 and 2), classified by purpose (Section 4): an API call whose purpose is reset is a reset action; a UI interaction whose only purpose is to reach a control or a view is a navigation action; a read used to verify is classified by its mechanism (Section 5, rule 8).
3. Navigation rule, uniform for every web condition (reviewer's ruling of 2026-10-06, to be confirmed in the START decision package): when observing the surface after the reset requires a page load or a route change, that navigation action is performed and counted, identically for every SUT; when the view updates without navigation, no navigation is performed. Each web row states whether a navigation is needed and the source line that makes it so. A navigation needed to reach the reset control is a navigation action under Section 4 in the same way (SUT-02 row; item Q4 of section 11). Clarification recorded after DEVELOPMENT run DV0008 (2026-10-06); basis: the W-B exclusion of Phase A: a page load that would discard business state which the mapping's reset mechanism left in the running client is a reset mechanism, not an observation, and is not performed where the mapping does not list it (row 4.4).
4. Evidence capture is not an action: screenshots, DOM text, storage snapshots, HTTP request and response transcripts, and process trees captured alongside an action record the observable effect of that action. Every capture runs after the outcome criterion of its action or step has been evaluated, and a capture that fails is recorded under `evidence_errors` on that record without changing any outcome (Phase B, after review during the DEVELOPMENT runs of 2026-10-06; section 12).
5. Completion criteria belong to their action: Playwright's own actionability waits (each with an explicit timeout), an HTTP request's timeout, and the SUT-05 port-refused and readiness waits are recorded as evidence (number of polls, elapsed time), never as further actions; otherwise the count would depend on a polling interval.
6. Retries: none is predeclared. A failed action keeps its outcome; the run goes on to the verification where the row says so. A retry would be a further record with `is_retry` true; none is performed.
7. Declared target state and its view: the declared target state includes the view the surface is in after the establishment. A transient panel opened by the establishment itself is closed by the establishment (SUT-03 row; item Q3).
8. Per-action outcome (Section 5, rule 9): SUCCESS, PARTIAL_SUCCESS, or FAILURE, decided per action by the criterion stated in the row.
9. Run outcome (`outcome.status`): SUCCESS when the post-reset oracle predicate holds; FAILURE when it was evaluated and does not hold; INCONCLUSIVE when the post-reset observation could not be classified; ABORTED when the run stopped before the first reset-side action (empty `actions[]`, cause in `notes` and `precondition.json`; the measured workflow's validation step then fails by design while the bundle is still uploaded); ERROR for a runner or infrastructure fault (a manifest is still written when possible).
10. Surface-control rule, uniform for every web condition (reviewer's rule of 2026-10-06T02:12:51Z, which makes the human research lead's decision on item Q5 uniform; restated for confirmation in the START package): on a web condition the reset is triggered through the web surface's own control when the pinned surface offers one that performs the mapping's reset mechanism (SUT-02: 'Reset App State' in the drawer; SUT-03: 'Logout'; SUT-04: the booking row's delete control); otherwise it is performed through the mapping's endpoint. The requests, re-fetches, and route changes of a control's own handler belong to that one action. SUT-01's pinned web surface offers no reset control (a search of `frontend/src` at the pin finds no call to `/api/session` or `/api/session/reset`), and its documented client "Reset recipe" (`ATOMIC_WEB_TESTING.md:175-183`) is a localStorage-clearing procedure, a client-storage clear that the frozen mapping does not list (the reason W-B is excluded); W-A therefore applies to SUT-01 (section 4.2).
11. Starting-state check: when the read of the declared starting state before the establishment does not hold, the run stops as ABORTED, with the cause in `notes` and `precondition.json` (reviewer, 2026-10-06T02:12:51Z).

## 9. Implementation integrity

Gate G-10 and the executor step of the measured workflow hash only `run-condition.sh`. `run-condition.sh` therefore embeds the sha256 of every other implementation file (`executor/*.py`, `requirements.txt`) and verifies them, and the absence of any unlisted Python file under `executor/`, before anything else; any mismatch exits non-zero without writing a manifest. The single hash locked at START thereby covers the whole implementation without a workflow change. `requirements.txt` pins Playwright for Python by exact version with sha256 hashes (`--require-hashes`). In hash-checking mode pip refuses any requirement that is not pinned by exact version with hashes, so `requirements.txt` also lists the runtime dependencies that the pinned Playwright version declares in its package metadata, each by exact version with the hashes of its wheels for the measured substrate (ubuntu-24.04, x86_64, CPython 3.12) and for the DEVELOPMENT workstation; these dependencies were read in Phase B from the pinned version's metadata: Playwright for Python 1.63.0 (the newest stable release on 2026-10-05; Requires-Python >=3.10) declares `pyee<14,>=13` and `greenlet<4.0.0,>=3.1.1`, and pyee declares `typing-extensions`; pinned: pyee 13.0.1, greenlet 3.5.6, typing-extensions 4.16.0, installed with `--require-hashes --only-binary :all:`. Chromium is not a Python requirement: `playwright install chromium` downloads it from Playwright's download host; its build is the one the pinned Playwright version names (chromium-1243, Chrome for Testing 153.0.8010.12), the study does not hash-pin it, and its version is recorded per run. At start the executor checks the installed Playwright version against the pin and records the observed versions of Chromium, python3, and bash in `tool-versions.json` and `toolchain`.

Implementation (Phase B). `run-condition.sh` requires the variables the measured step sets (`CONDITION_ID`, `ASSIGNED_SUT`, `EXECUTION_ID`, `ATTEMPT`, `EXECUTOR_PROMPT_VERSION`, `OUTPUT_DIR`, `PROVENANCE_JSON`, `RUNTIME_ENVIRONMENT_JSON`) and `RECORD_CLASS`, verifies the embedded digests and the absence of unlisted Python files, refuses an existing `run-manifest.json`, and runs `python3 -m executor.run` with `PYTHONDONTWRITEBYTECODE=1`; `python3` on PATH must be the interpreter where `requirements.txt` is installed. `executor.run` refuses without writing a manifest (exit 2) when `RECORD_CLASS` is not MEASURED_EXPERIMENT, DRY_RUN, or DEVELOPMENT; when MEASURED_EXPERIMENT is set outside `.github/workflows/e03-measured-execution.yml` (`GITHUB_WORKFLOW_REF`); when the condition has no realization here or does not belong to `ASSIGNED_SUT`; when the execution id is not EX, DR, or DV followed by four digits for MEASURED_EXPERIMENT, DRY_RUN, or DEVELOPMENT, or the attempt is below 1; when the name of `OUTPUT_DIR` is not the run id; when a manifest already exists; or when the installed Playwright for Python is not the pin. Every text the executor writes passes a scrubber when the file is written: registered secrets and JWTs become `<redacted-token sha256:...>`, and host paths become `<output>`, `<executor>`, `<instance>`, `<workspace>`, `<cwd>`, `<home>`, or `<tmp>`. A secret that is not a JWT is caught only once it is registered: SUT-04's cookie token, known only from the login response, is registered on receipt, and the login transcript, which `Run.http` has already written, is rewritten through the scrubber before any other evidence file is written (DEVELOPMENT run DV0011 found the gap, DV0013 verifies the fix; section 12, defect 3). Since operation OP-PREP-E03-REV-01, `Run.http` registers the value of every cookie a response sets (each `Set-Cookie` header, whatever the cookie's name; a value shorter than eight characters is not registered) before it writes the transcript, so no HTTP transcript holds such a value in clear; the SUT-04 rewrite above stays and has then nothing left to replace (section 12, item 7). The scrubber does not replace the operating-system login name that some SUT logs print (each SUT-04 service's start-up line reads 'started by <user> in <path>', whose path is replaced): on the GitHub-hosted runner it is the runner account, not a private name, and DEVELOPMENT bundles never leave the operator's scratch area (decision of the human research lead of 2026-10-08, option A, given to the study's independent orchestration reviewer and relayed). The HTTP client is the standard library's, without proxy, redirect following, or retry; each transcript keeps the first 64 KiB of the body. A web run uses one headless Chromium context (viewport 1280 x 800, time zone UTC, locale en-US) and keeps its network and console events as evidence. `executor.log` is completed and closed before the manifest is built, so its listed sha256 is that of the final file (section 12, defect 1).
