## 3. One execution: three loads, a rotating order, nothing restarted

One execution is three page loads of the same condition, each in a **fresh browser context** (no cache, storage or cookies carried over): the degraded load **D**, an earlier baseline load **Ba** and a later baseline load **Bb**. The order rotates over the absolute execution index i: (D, Ba, Bb) for i mod 3 = 1, (Ba, D, Bb) for 2, (Ba, Bb, D) for 0, so that the degraded load takes each position (16, 17 and 17 times in 50 executions) and a drift of the runner acts on both kinds of load (E08-D-9). Detection compares D with Ba; the false-positive record compares Bb with Ba under the same rule. Nothing is restarted between executions (a page load changes no state of the SUT); the instance is provisioned once per job.

Blocks of one execution, in order: **starting-state check** (the surface answers; for SUT-01 the API health answers and both accounts log in with the behavior the condition declares, the activation record; for SUT-02 and SUT-03 the login is part of each load), **method** (the three loads), **classification**, **record** (run manifest last). Before the first measured navigation the execution has sent nothing the SUT could count as a measurement; an exception before it is attributed to TOOLING, after it to the SUT (rule D-16 of E05).

Per load: SUT-01 logs in through `POST /api/auth/login`, seeds the client state of the E03 SUT-01 web realization (market MX, language es, the token, an empty cart) on a first load of the web root, then navigates to `/catalog`, waits for the first catalogue item (up to 20 s) and 1 s more. SUT-02 logs in through the login form (the session is a cookie), waits for the inventory list (for the glitch account the application blocks 5 s while it renders after the login, and that block is not measured), then navigates to `/inventory.html` as a full document load, waits for the inventory list (up to 30 s) and 1 s more. SUT-03 logs in through `/sut/login` (the dummy credentials its own labels show), then navigates to the page and observes it for a fixed window of **8000 ms** from the start of the document (E08-D-12: longer than the 4.5 s end of the layout transition of the CLS page and than the 3 s image delay plus a fetch). The measurement script (executor/probe.py) is present from the start of every document and reads only the browser's own Performance APIs.

## 4. Metrics, detection rules, categories (written before any DRY_RUN; a DRY_RUN may expose a defect but does not choose them)

- **first_item_ms**: `performance.now()` of the document at the first attachment of an element matching `h2[data-testid^="pizza-name-"]`.
- **longest_longtask_ms**: the largest duration among the Long Tasks entries of the document; the API observed and no entry is 0 ms; an unsupported API is `INCONCLUSIVE_METRIC_ABSENT`.
- **lcp_ms**: `startTime` of the last Largest Contentful Paint entry within the window.
- **cls**: the web.dev definition, the largest sum of the shifts without recent input over session windows (a window ends after a gap of 1 s or at 5 s).
- **Rule.** DELAY, BLOCK and LCP: `metric(D) - metric(Ba) >= threshold`. CLS: `cls(D) > cls(Ba)` **and** at least one shift entry of D at or after 3500 ms whose sources include the element with id `target-text`. The false-positive record applies the same difference rule to (Bb, Ba) (for CLS: `cls(Bb) > cls(Ba)`, the target clause having no element to name on the baseline page).
- **A load counts only if the page showed its own content** (`required_ready`: the first catalogue item, the inventory list, or the page's heading); a login page or an error page is `INCONCLUSIVE_READY_SIGNAL_MISSING`, never a non-detection. A missing signal of Bb only removes the false-positive record of that execution.
- **Categories.** `DETECTED` (SUCCESS; matches expected), `NOT_DETECTED` (FAILURE; a recorded non-detection, not an error), `INCONCLUSIVE_READY_SIGNAL_MISSING`, `INCONCLUSIVE_METRIC_ABSENT`, `INCONCLUSIVE_EXTERNAL_IMAGE_NOT_LOADED` (LCP only: the delayed image of the external host was not painted as a largest-paint candidate of D; attribution EXTERNAL; never a non-detection, because the host is outside the evaluated version, SUT03-EV-0013), `START_SURFACE_NOT_READY` and `START_ACTIVATION_NOT_CONFIRMED` (ABORTED), `INTERRUPTED_` (ERROR), `STUB_NO_BUNDLE` (ERROR). There is no catch-all: an undeclared label is kept with a note so that the analysis fails closed on it.
- **Denominators (E08-D-18, predeclared before any data).** The detection proportion of a condition is the number of `DETECTED` executions over the number of executions that are valid measurements (`DETECTED` or `NOT_DETECTED`); every `INCONCLUSIVE_*`, `START_*`, `INTERRUPTED_` and `STUB_NO_BUNDLE` execution is reported with its count and its attribution and sits outside that denominator (the E09 precedent: a recorded attempt that is not a ground-truth instance is excluded from the detection denominator and is never a rate of zero). The false-positive proportion is the number of executions whose baseline-against-baseline record is true over the number of executions that have such a record (both baseline loads valid), whatever the category of D. All N = 50 executions of a condition appear in the table of counts. No minimum number of valid executions is invented.
- **Reporting** (the analysis, later): per condition the proportion of executions that detect the degradation and the baseline-against-baseline false-positive proportion, each with a Wilson 95% interval, the medians descriptive; per ecosystem the H5 count; no ranking and no composite; a near-certain result stated as controllability evidence of the ground-truth condition and of the measurement, never as discriminating power (E08-D-7).
