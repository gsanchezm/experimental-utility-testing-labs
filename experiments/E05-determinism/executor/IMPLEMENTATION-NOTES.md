## 1. Shape of the work (14 conditions, four systems under test)

Fourteen conditions, N = 50 each, 700 attempts: SUT-01 7 (API 6, web 1), SUT-02 2 (web), SUT-04 3 (web 1, API 2), SUT-05 2 (API). SUT-03 has no condition. Dispatch model B (D-02): one measured dispatch per condition, so 14 dispatches, each running its 50 executions on one shared instance. Four per-SUT dispatch authorizations (Section 3.7 of protocol/agent-governance-v6.md) would cover them (SUT-01, SUT-02, SUT-04, SUT-05).

## 2. Design points fixed here before any code (each is confirmed at START)

1. **Attempt order inside one execution** (brief s.2.1): reset, starting-state check, establishment, target-state verification, stimulus, classification, record. The starting-state check failing is ABORTED with its cause; target-state verification failing stops the attempt before the stimulus and carries an ESTABLISHMENT_ category (outside the CEOR denominator, inside TSRR and E2E-ROR).
2. **Continuation rule (this draft states what config s.6 left open):** after an ABORTED, ERROR or INTERRUPTED_ execution the job goes on to the next execution of the same condition; a failed attempt is an outcome, never a stop (protocol/repeatability-determinism-v1.md, section 5, rules 4 to 6). Only a gate or provenance failure of the job itself stops it, and then the executions not started have no record at all.
3. **Bundle layout:** one workflow artifact per dispatch. Inside it, one directory per execution, `executions/<condition_id>__EXnnnn__A1/`, with the full bundle of that execution (run manifest of schema v2 last), plus a counts-only `condition-summary.json` written by the job. The import writes 50 directories under `raw-data/E05-determinism/<SUT>/` per dispatch, so the dispatch tool of E09 adapts mechanically.
4. **Partial-upload survival:** the executor writes each execution's files completely before the next execution starts; the upload step runs with `if: always()`. If the runner dies at execution k, executions 1 to k-1 are complete and importable; executions k to 50 have no record, and replacing them is a further attempt under a recorded further-attempt approval (the pattern of operation OP-CI-18), never a re-run.
5. **No-bundle accounting (D-09):** an execution that left no bundle but whose attempt began gets a stub record (STUB_NO_BUNDLE, outside S); the stub counts against TSRR and E2E-ROR and never against CEOR.
6. **SUT-01 process-restart reset (D-03 b; API-01, API-06, WEB-01):** a new realization. The E03 verification workflow starts SUT-05 and the six SUT-04 services each in a new session and process group (start_new_session, group recorded, SIGTERM to the whole group, port must refuse connections before the stop is evaluated), but its SUT-01 provisioning records no process group and no `process` block. The E05 workflows provision SUT-01 on the same pattern and write a `process` block into `instance.json` (shape as the SUT-05 block of the E03 workflow: pid, pgid, start_command, cwd, env). After each restart a web condition logs in again and re-injects client state, because the restart clears the in-memory session store.
7. **SUT-04 message service (SUT04-API-02):** settled statically from the E03 workflow: the SUT-04 route starts six services, among them `message` on port 3006, so the measured instance runs the real message service and not a double. The endpoint was then read (manifests/source-reads-v2.yaml, SOURCE-READS-02, 2026-11-13, on the human research lead's approval): GET {message}/message/ lists the posted messages (body {messages: [...]}), GET {message}/message/count counts them, both without a token; port 3006, context path /message (findings F13 and F14). A message needs a phone of 11 to 21 characters (F15), so the phone of the SUT04-API-02 stimulus must satisfy that for a message record to exist. `instance.json` gets a `message` base URL.
8. **Browser context across the 50 executions of a web condition:** one context per condition, kept across executions, so the reset is a real measurement (the substance of model B); a context or browser crash before the stimulus is a TOOLING interruption (D-16) and a new context is created and recorded. Fresh context per execution would make the reset of SUT-02 (APP_DATA_CLEAR) nominal, so it is not used.
9. **DRY_RUN override:** the environment-verification workflow runs 2 or 3 executions per condition, labeled DRY_RUN, never 50. It also checks finding F10 (the SUT-04 web conflict shows no message) and probes the message service endpoint.
10. **Job time budget:** SUT-05 conditions run 50 environment restarts (readiness budget 180 s each); `timeout-minutes` is set per condition from the measured duration of a DRY_RUN execution, below the 6 h job limit.
11. **API-01 expected total:** computed from the constants and the catalog and rate tables of the pinned commit (finding F02 of manifests/source-reads-v1.yaml names backend/constants.py lines 89-100); recorded as a config constant before START, never read from a run.
12. **Implementation integrity:** `run-condition.sh` carries embedded digests of every implementation file and refuses unlisted Python files (the E02 and E09 pattern); no literal name of the agent-instructions file appears in any executor file, workflow, or comment (the export aliases it and breaks digest checks); the run script of a gate step stays under 21000 characters when it carries an expression, and dispatch inputs reach it through `env` (operation OP-CI-15).

13. **SUT-04 names and dates are stable per condition, and the reset finds its bookings by listing.** The E03 realization derived the guest names and dates from the run id, which is right for a fresh instance per run. On one shared instance the starting-state check would then hold trivially after a failed reset (no booking has the new run's names), so a reset that did not hold would be invisible. In E05 the names and the far-future dates are a function of the condition id; the reset deletes every booking of room 1 that carries them (found by listing, so an execution interrupted before its own cleanup leaves nothing that no later reset deletes); the starting-state check then reads that none remains. Confirmed in the tests: a reset that fails (HTTP 500) is RESET_FAILED and a reset that answers 202 without deleting is RESET_STARTING_STATE_NOT_REACHED. To be confirmed at START.
14. **SUT-01 web re-injects client state at every execution.** After the process restart the in-memory session store is empty, so the web condition logs in again and writes the E03 client keys (token, market, empty client cart) before the starting-state check. The injected client cart is empty by construction, so that part of the check cannot reveal client-side residue; the server cart (cleared by the restart) is what the check measures.
15. **Phase mapping and attribution (implemented in classify.label_for_failure and attempt.failure_outcome, tested in tests/test_attempt.py).** reset: RESET_FAILED; starting-state: RESET_STARTING_STATE_NOT_REACHED (status ABORTED with its cause); establishment: ESTABLISHMENT_FAILED, or ESTABLISHMENT_INTERRUPTED for an exception; verification: ESTABLISHMENT_VERIFICATION_FAILED, or ESTABLISHMENT_INTERRUPTED for an exception; stimulus or classification: INTERRUPTED_. TOOLING is assigned only to an exception raised before the stimulus request is sent (the realization calls run.mark_stimulus_sent() immediately before it sends it); a recorded failure, an exception after the send and every uncertain case are SUT (D-16 rules 1 to 3). A recorded failure of the SUT or the instance in a pre-stimulus block is not an exception, so it is SUT.
16. **Conditions that cannot run yet (the START package decides).** E05-SUT02-WEB-02 is not configured (run.py refuses it): its 'visual marker' (row SUT02-EV-0015) is defined by no recorded source (SOURCE-READS-03, F23). The SUT-01 web stimulus (E05-SUT01-WEB-01) locates the tid controls with contains selectors because tid comes from a hook that no file read defines (F22); the first DRY_RUN confirms them. E05-SUT04-API-02 declares no catch-all category, so a count that is unreadable or jumps by more than one is written as the undeclared labels S_MESSAGE_COUNT_UNREADABLE and S_MESSAGE_COUNT_UNEXPECTED, which the analysis must fail closed on (decision for START: add S_OTHER with k = 5, or keep the gap).
17. **Expected values come from the pinned source, never from a run.** executor/expected-sut01.json is derived statically from backend/constants.py by executor/tools/derive_sut01_expected.py (hash-checked against SOURCE-READS-01); the expected checkout of E05-SUT01-API-01 is 340.26 MXN (subtotal 263.07, delivery fee 35.1, tax 42.09, tip 0; SOURCE-READS-03, F16); the lockout message of API-03 is 'Sorry, this user has been locked out.' (F19); the a11y modes of API-05 are decided from the body against the pinned catalog (F18). The projection of API-05 cannot tell a wrong_lang draw whose names all equal the English ones from the standard catalog; such a draw is S_OTHER.
18. **Message service read.** After the accepted booking of E05-SUT04-API-02 the executor reads GET {message}/message/count (answering {count: n}, F24) once before and after, waiting up to 5 s in steps of 0.5 s for the count to rise; whether the message is posted synchronously is not known from the files read, and the first DRY_RUN shows it. This wait is an observation window, not a retry of the stimulus.

19. **Ratification and the decisions taken with the workflows (2026-11-13).** The human research lead answered 'si a todo' to the report that listed: the reading of his answer of 2026-11-12 (question dialog 2 of manifests/campaign-execution-decisions-v6.yaml) as covering the three files of manifests/source-reads-v3.yaml that earlier lists did not name (backend/routers/auth.py, backend/auth.py, message/.../Count.java), and five decisions on the workflows: gate G-9 (the locked configuration names the sha256 of the measured workflow file; consistent with config s.13, item 7), the verification workflow failing on ABORTED, ERROR and TOOLING executions, the verification target 'all' being red by design for E05-SUT02-WEB-02 while it is unconfigured, no further-attempt input in the workflows (the OP-CI-18 record is per execution), and the working prompt prompts/working/ORCHESTRATOR-E05-determinism-v1.md. That answer is recorded here as given; it approves no export push, dispatch, START or authorization.
20. **Import layout (proposal, fixed by the locked configuration at START).** The measured artifact root holds `executions/<run_id>/` x50, `condition-summary.json`, `sut-logs/` and the four job-level files. The import writes each execution directory to `raw-data/E05-determinism/<SUT>/<run_id>/` (the path its manifest lists) and keeps the job-level files in `raw-data/E05-determinism/<SUT>/<condition_id>__job/`; the H3 loader (written after the lock) reads the run directories and ignores `*__job`. The dispatch record and the import record name this layout.
