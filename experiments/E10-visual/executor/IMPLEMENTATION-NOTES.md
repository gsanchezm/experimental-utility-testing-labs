# E10-visual executor: implementation notes (DRAFT, operation OP-PREP-E10, 2026-11-28 UTC)

Not frozen, not locked. These notes say what the implementation derives from, what it decides, and what is open. They are not a result and not a decision of the human research lead. No claim below is an observation of Chromium, of a SUT or of a registry beyond what the cited source files and the registry metadata of 2026-11-28 show.

## 1. Derivation

The framework (job context, run, scrubber, evidence, manifest builder, attempt loop, the digest lock, the instance interface, the entry checks) is copied from the E08 executor and, through it, from E11 and E05 (each campaign locks its own copy; nothing is imported from another campaign path at run time). The SUT-01 API login and client-state seeding are those of the E08 and E09 executors (the E03 SUT-01 web realization); the SUT-02 login form is E08's; the SUT-03 sign-in flow is the E03 SUT-03 web realization and the login of the performance test area (with its hydration wait) is E08's. The pinned-tarball route follows the precedent of the E09 axe-core pin (experiments/E09-accessibility/executor/executor/scanner.py): a registry tarball verified by digest and read in memory. What is new in E10: the capture helpers (capture.py), the comparison instrument and the PNG codec (compare.py), the rule, the calibration function and the external-image rule (classify.py), one execution as per-view captures A, B, A2 in fresh contexts (attempt.py, sut01.py to sut03.py), and the refusal of a measured run whose thresholds are not calibrated (run.py).

## 2. Choices made in the implementation (each is a HUMAN DECISION of campaign-configuration-draft.md, section 7, or a harness fact)

1. **Fresh context per capture, one Chromium per job.** A context has its own cache, storage and cookies, so one capture cannot warm another and the login of one capture cannot leak into the next. The Chromium process is shared. E10-D-16 (fixed order A, B, A2, no rotation).
2. **Viewport screenshots only.** Every capture is 1280 x 900 CSS pixels at scroll position 0, so two captures are always the same size and Pixelmatch (which refuses unequal sizes) can compare them. A capture of another size is `INCONCLUSIVE_CAPTURE_DIMENSION_MISMATCH`. "Every item" therefore means every item wholly inside the first screen (E10-D-4); the elements are found by their selectors in A and the set is fixed by A.
3. **The box clause uses boxes read from the DOM.** `getBoundingClientRect` of each element at capture, in A and in B; the region is their union clipped to the capture; a box of zero area contributes nothing (the SUT-03 `#shift-target` before its mutation). An expected group with no element wholly inside the viewport in A is `INCONCLUSIVE_READY_SIGNAL_MISSING` (the configuration draft does not say what happens in that case; a conjunction over zero elements must not read as a detection, and it must not read as a non-detection either).
4. **The mask comes from the output of Pixelmatch.** The runner returns the diff image and a one-byte-per-pixel mask built from the library's diff colour (255, 0, 0, 255), which no gray pixel of the output can have and which the anti-aliasing colour (255, 255, 0) differs from. The count of marked pixels must equal the count Pixelmatch returns, or the comparison is refused. The options are the library defaults (`threshold` 0.1, `includeAA` false, `alpha` 0.1), passed explicitly and recorded; version 8.0.0 measures the colour distance in the OKLab colour space (its documentation), which is a property of the pinned version and is not tuned.
5. **Standard-library PNG.** Chromium screenshots are decoded in pure Python (8-bit RGB or RGBA, not interlaced, the five filter types, CRC checked), so that no image dependency is pinned beyond Pixelmatch itself. Rows of the filters Average and Paeth are decoded byte by byte; their cost on real screenshots is a DRY_RUN item (section 3).
6. **The Node.js runner is a Python string constant** (`NODE_RUNNER_JS`), written to a temporary `runner.mjs` at run time, so that it sits under the digest lock; the verified module is written as `pixelmatch.mjs` (the registry file is ESM and has no package.json beside it, so the `.mjs` extension is what makes Node.js read it as a module). Its digest is recorded in `evidence/instrument.json`.
7. **Thresholds.** `conditions-draft.json` carries a `thresholds` pair `{T_R, T_e}` per condition (null in the draft; a pair in `rule` is refused). At the configuration lock the pair is written there from the calibration record. With the pair null the floors are used, `thresholds.provisional` is true in every detection record and in `evidence/instrument.json`, and a MEASURED_EXPERIMENT is refused by `run.check` (fail closed).
8. **`required_ready`.** A capture whose page never showed its own content cannot be a measurement; a login page screenshot compared with a catalogue screenshot would otherwise be recorded as a detection or a non-detection. A missing signal of A2 only removes the false-positive record of that view (E08 precedent for its later baseline).
9. **Timed captures.** For the `high_cls` view the capture waits for `performance.now() >= capture_at_ms` of the measured document (origin: the start of the navigation), then settles and takes the screenshot, then reads the clock again. A capture whose clock after the screenshot is more than 1000 ms past the target is `timed_ok` false and the view is `INCONCLUSIVE_READY_SIGNAL_MISSING` with the reason `CAPTURE_TIME_MISSED` (the declared categories have no member for a missed time; this is the closest). The tolerance is a constant of capture.py, not a value derived from any run.
10. **The external-image rule** (SUT-01): every expected element of a group flagged `image` that is wholly inside the viewport in A must have `complete` and a natural width above zero in A and, when A2 is a valid capture, in A2; otherwise `INCONCLUSIVE_EXTERNAL_IMAGE_NOT_LOADED`, attribution EXTERNAL. The state of the images of B (loaded placeholder or broken) is recorded per element and is never a validity condition. No request is intercepted, rewritten or answered: the SUT is evaluated as found.
11. **No secrets are registered for SUT-03.** `password` (test area) and `testingisfun99` (sign-in page) are shown by the pages themselves and the first is a word that occurs in every form field name. The SUT-01 password (`pizza123`) and the SUT-02 password (`secret_sauce`) are registered with the scrubber. PNG screenshots are not scrubbed (they are not text); a screenshot could show a signed-in user name, which is not a secret.
12. **Time budgets.** Watchdog 1500 s per execution and the job limits are provisional (E10-D-19): the longest execution is nine captures of SUT-02, each with a login and several waits of up to 20 to 60 s. They are re-set from the DRY_RUN durations before the START, never from any outcome. The per-capture waits are the constants of capture.py and the realizations.
13. **`behavior_class`.** `external dependency` for SUT-01 (the images of upload.wikimedia.org and the failing host), `deterministic` for the others. The schema enum is used as it is.
14. **SUT-01 behavior check.** Both accounts must answer with the behavior the condition declares (`standard` for State A, `problem` for State B; the values of `UserBehavior` in backend/constants.py at the pinned commit), as in E08, otherwise `START_ACTIVATION_NOT_CONFIRMED`.
15. **One comparison per pair, per view.** A against B and A against A2 are compared once each; the per-element ratios of A against A2 are recorded beside the whole-frame ratio, as input of the calibration rule (`classify.calibrate`), which is a pure function and is not called by the executor itself: the calibration record is written by the ORCHESTRATOR from the DRY_RUN rounds, under the human research lead's approval, before the START.

- Whether the checkout button of the `cart` view and the close icon of the `menu_open` view lie wholly inside the viewport in State A, and where the cart icon container and the burger icon are in State A and State B.
- What Chromium paints for an `<img>` with an empty source on the SUT-03 shelf, how many thumbnails lie inside the first screen, and whether `navigator.connection.effectiveType` (recorded in every capture) is anything that changes the shelf (the E03 note on the `2g` message).
- Whether the 2000 ms and 5500 ms captures of the `high_cls` view are taken in time (`doc_time_after_ms`), and what the box of `#shift-target` is in A and B.
- The baseline-against-baseline ratios (A against A2: whole frame and per element), the only input of the calibration; whether any pair exceeds the floors.
- The PNG sizes per capture and diff image (the retention rule, E10-D-20), the decoding and comparison time per capture (pure-Python filters), and the durations of the executions (E10-D-19).
- The version strings of Playwright, Chromium and Node.js, and the Node.js version of the runner image, for the entry `tools.visual`.

## 4. Known limits

- The first screen only: elements below the fold are never captured, so "every item" is a subset by construction (E10-D-4); the mechanisms are uniform across items in the evidence records, which is why the subset is read as representative, and the limit is stated in every report.
- The pixel comparison measures what is on screen. A difference outside every expected region is recorded (`unlisted_diff_ratio`) and never counted as a detection or a false positive.
- A text node and its font rendering depend on the runner's fonts; the baseline pairs of the DRY_RUN rounds are the only evidence of how stable they are, and the calibration rule is the only response to them.
- The Pixelmatch tarball is downloaded at run time from the public registry (one attempt); a registry outage refuses a run before any record is written (exit status 2), which is a visible, non-recorded refusal, not a finding.
- The decoding of PNG in pure Python is slower than a native decoder; if the DRY_RUN durations show it matters, the alternative is a second pinned module in the Node.js runner, which is a new pin and a new decision.
- Nothing here measures load: one sequential client, no significant load.
