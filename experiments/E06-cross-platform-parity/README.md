# E06 — Cross-platform Parity

## Objective

Determine whether logically equivalent scenarios exist across the Web, Android, and iOS surfaces of each evaluated ecosystem (each a system under test, SUT), and whether those scenarios produce equivalent observable outcomes when executed. Parity is assessed per scenario per platform; the presence of three applications does not imply parity, and each claimed equivalence must be demonstrated by execution or explicitly recorded as absent or untested. Equivalence across platforms within an ecosystem, and across ecosystems, is semantic equivalence under protocol/equivalent-scenario-mapping-v1.md; every scenario used for inferential comparison has a FROZEN mapping record before this campaign executes, and an ecosystem without a defensible semantic equivalent is NOT_COMPARABLE for that scenario (not a score, not a zero). Mobile executions use the runner selected under protocol/mobile-runner-policy-v3.md, and only for ecosystems that passed the per-SUT compatibility smoke (section 9); the smoke is a tooling prerequisite and produces no evidence about any ecosystem.

### Outcome categories, pairing and the parity proportion

- Outcome categories (declared before any execution in the conditions file; D-E06-5 to D-E06-9 and D-E06-12 to D-E06-15): ARRIVED_IDENTITY_READ (status SUCCESS: the authenticated catalogue was reached and the identity of the first position was read); ARRIVED_ARRIVAL_ONLY (SUCCESS: reached, identity oracle arrival_only; not used); ARRIVED_IDENTITY_UNREADABLE (INCONCLUSIVE: reached, identity not readable, recorded with its reason); NOT_ARRIVED_INFRASTRUCTURE (ABORTED: the backend refused or did not answer, or the device did not answer in time; reasons INFRA_USER_LIMIT_429, INFRA_BACKEND_5XX, INFRA_BACKEND_NO_RESPONSE, INFRA_CATALOGUE_TIMEOUT); NOT_ARRIVED_SUT (FAILURE: the system answered and did not let the actor through; reasons SUT_SIGN_IN_REFUSED, SUT_CATALOGUE_NOT_REACHED_AFTER_SIGN_IN); NOT_ARRIVED_RUNNER (ERROR: a fault of the executor, the browser, the WebDriver client or the Appium session; reason RUNNER_FAULT). The expected outcome of every condition is ARRIVED_IDENTITY_READ.
- Pairing and parity (decisions D-E06-7 and D-E06-15; computed only by the analysis, never by an execution, a dispatch or the condition summary): execution k of the WEB condition of an ecosystem is paired with execution k of its ANDROID condition (same account, same market, same index), k = 1 to 50. Parity is present for pair k when both executions reach the authenticated catalogue and the identity of the first catalogue position is the same on both surfaces. An execution that did not arrive is recorded with its category and reason and is a non-parity, never excluded after the fact and never retried inside the same execution record. An execution that arrived with an unreadable identity is a non-parity as this rule is written, and the analysis reports it as its own category beside the parity counts, never merged silently and never excluded. The pairing is by index, not simultaneous: the two conditions of an ecosystem are separate dispatches (see "Sample size, order and dispatch model").
- Primary variable and estimand: the parity proportion per ecosystem, pairs with parity over 50, with a Wilson 95 percent interval; the effect SUT-01 versus SUT-02 by risk difference with an interval and Fisher's exact test (protocol/statistical-analysis-plan-v1.md, section 4.3). Descriptive in weight, because one canonical scenario gives one scenario pair per comparison.

### Attribution and exclusion rules

- No attempt is excluded from any denominator. A non-arrival is data: a backend refusal such as the user limit answer HTTP 429 (INFRA_USER_LIMIT_429) is recorded with its message, never repaired and never excluded (D-E06-8).
- Attribution is mechanical, declared before the run and never applied after seeing a result pattern (as implemented in experiments/E06-cross-platform-parity/executor/executor/classify.py; confirmed by the human research lead's approval of this text at the START): NONE for an execution that arrived; SUT for NOT_ARRIVED_SUT; INFRASTRUCTURE for NOT_ARRIVED_INFRASTRUCTURE; TOOLING for NOT_ARRIVED_RUNNER; UNDETERMINED for ARRIVED_IDENTITY_UNREADABLE (the cause is not assigned mechanically, and the record says so). The reason of a non-arrival is decided by a fixed precedence (the first matching rule wins): the user limit, a 5xx answer, no answer within the budget or the sign-in page never shown, a refused sign-in or an unestablished session, a catalogue that was reachable and not shown, a catalogue that never answered, and, last, a sign-in that was never submitted (RUNNER_FAULT). The Android applications cannot report backend answers, so a sign-in with no refusal shown within the budget is INFRA_CATALOGUE_TIMEOUT there, and is disclosed as such.
- Any exception inside an execution (browser, executor, WebDriver client, Appium session) is NOT_ARRIVED_RUNNER with attribution TOOLING and the message recorded, and the job goes on with the next execution; an exception that leaves the loop ends the condition with the summary of the executions already run and a non-zero exit, which is a failure of the measured job and a stop of the procedure. A runner cancelled or lost by the workflow leaves an incomplete bundle; the ORCHESTRATOR records such an execution at import as TOOLING of that execution (not implemented by the executor; confirmed by the human research lead's approval of this text at the START).
- The executor scrubs host paths and private network addresses from every kept text file; no secret is recorded.
