# E01 — Capability Audit

## Objective

Apply the capability rubric defined in protocol/capability-rubric-v1.md to all nine testing modalities for each of the six evaluated ecosystems (each a system under test, SUT), and describe the eight cross-cutting properties defined in protocol/cross-cutting-properties-v1.md for each ecosystem. The audit records, with provenance, what each ecosystem provides for each modality and how controllable, resettable, deterministic, and observable those provisions are. E01 is an audit (a structured evaluation of artifacts and documentation), not an execution campaign; its outputs are provisional until reviewed by ADJUDICATOR-EU-01 per protocol/agent-governance-v1.md.

## Related research question(s)

- RQ1 Experimental Breadth (primary).
- RQ2 Controllability, Observability, Automation Affordances, and Setup Effort (secondary, descriptive: the Observability and Automation Affordances cross-cutting property descriptions are the basis of dimension 5).
- E01 feeds all six dimensions of the Experimental Utility profile; dimension 1 Experimental Breadth primarily.

## Future independent variables (candidate — not frozen)

- Ecosystem (SUT-01 through SUT-06) — candidate.
- Testing modality (the nine frozen modalities, in protocol order) — candidate.

## Future dependent variables (candidate — not frozen)

- Provisional rubric score per ecosystem × modality cell (0–3, per protocol/capability-rubric-v1.md; Score 0 for a structurally absent surface, with its structural_scope_note; no N/A level) — candidate.
- Distribution of evidence statuses (DOCUMENTED, SOURCE_VERIFIED, EXECUTION_VERIFIED, INFERRED) across the cells of each ecosystem — candidate.
- Component presence per ecosystem (which surfaces, services, and artifacts are present, as declared with provenance) — candidate.
- Whether a controlled instance of the pinned version can be established per ecosystem (controlled_instance_available: true when every component surface that E01 confirmed present can be run by the study, from the pinned evaluated version, in a controlled environment (SELF_HOSTED or LOCAL for web and api service components; EMULATED or SIMULATED for android and ios application builds); false otherwise, naming the components that cannot; protocol/study-design-v1.md, section 10.5; an experimental-control fact, not a score) — candidate.
- Descriptive characterization of each cross-cutting property per ecosystem — candidate.

## Required evidence

- `audits/<SUT-directory>/evidence.csv`: one record per claim, with the exact field set and order defined in protocol/evidence-rules-v1.md (evidence_id, ecosystem_id, modality, provisional_score, evidence_type, repository, commit_sha_or_release, file_path_or_endpoint, mechanism, expected_behavior, evidence_status, structural_scope_note, notes). Every record carries a stable evidence_id (SUT0n-EV-nnnn) and provenance against the pinned target; unknown provenance is recorded as null, never guessed.
- `audits/<SUT-directory>/audit.md`: the narrative audit per ecosystem, covering all nine modalities and all eight cross-cutting properties, including structurally absent modalities recorded explicitly as Score 0 with a structural_scope_note, with evidence cited by evidence_id.
- A limitations section recording what could not be verified and why.
- A contradictions section recording conflicts between documentation, source, and execution evidence.
- Adjudication record from ADJUDICATOR-EU-01 before any E01 output is treated as non-provisional.
- Run manifest policy (protocol/evidence-rules-v1.md, "Execution verification records"): E01 is an audit and does not automatically require a run manifest. Evidence with status DOCUMENTED, SOURCE_VERIFIED, or INFERRED requires none. Every EXECUTION_VERIFIED record requires an execution verification record: a run manifest conforming to schemas/run-manifest.schema.json with campaign_id E01-capability-audit, run_id = verification_id (SUT0n-VR-nnnn), experiment_id `verification`, modality, environment_type, timestamp, sut_provenance, toolchain (probe), scenario (scenario or probe), outcome, artifacts, and related_evidence_ids, stored in `audits/<SUT-directory>/verifications/` with artifacts in `audits/<SUT-directory>/artifacts/`.
- Environment discipline: auditing may use official documentation, source inspection at the pinned version, PUBLIC_HOSTED deployments (non-destructive, session-scoped, within documented use), and controlled local execution when necessary (protocol/study-design-v1.md, section 10.2). No active testing against a public instance.
