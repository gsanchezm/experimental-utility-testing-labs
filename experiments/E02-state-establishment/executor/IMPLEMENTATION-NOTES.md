## 4. Conditions and scenarios: reconciliation with the briefs

- The conditions follow the design brief's set (HD-10): seven CS-003, three CS-004 (WEB for SUT-01, SUT-02, SUT-03). **The task text said that CS-004 maps SUT-01 API as well as WEB; CS-004 (DP-4, and the brief's HD-4) maps WEB only, and this draft follows the file.** No SUT-04, SUT-05, or mobile condition for CS-004 (CS-004 DP-7 and DP-8 leave them NOT_COMPARABLE or pending).
- Scenario ids are derived from the condition id (`E02-CS003-…` → CS-003; `E02-CS004-…` → CS-004); the scenario and the starting state are `CS-003` / `CS-003-STARTING`, `CS-004` / `CS-004-STARTING`; `target_state_id` equals the canonical scenario id (the E03 precedent; the brief's HD-note on the convention is open).
- Between-run reset: the brief and both mappings name a harness reset between runs (session reset, Reset App State, Sign-Out, booking delete, process restart). This draft provisions a fresh instance per run instead (section 6, HD-R). The mappings' reset realizations are therefore not executed.
- Starting-state check: the brief (HD-14) says the check is not counted and an unmet check gives ABORTED. The check is performed after the first counted identity action where the state needs the identity (SUT-01 WEB, SUT-02 WEB, SUT-03 WEB, SUT-04 WEB, SUT-05 API). ABORTED then keeps its counted actions (HD-A).
- CS-003 DP-3 and DP-5 discrepancies (brief HD-8): the SUT-02 oracle is UI-only (not named in DP-3), and the SUT-04 account is an administrator under "standard". Both are used as drafted: the realizations cite CS-003 and state the oracle and the account in their docstrings, but no manifest carries this disclosure. The brief asks for a decision before the START.

## 7. How a DEVELOPMENT or DRY_RUN would be made after approval

1. The human research lead approves a DRY_RUN of one condition (the verification workflow's `dry_run` must be true; `execution_id` `DRnnnn`; `executor_prompt_version` must name an existing working prompt; the implementation hash is the `run-condition.sh` sha256 of the commit). The verification gate passes on `main`. GitHub Actions evaluates only the public repository, so a DRY_RUN needs the export that publishes this executor and both workflows.
2. Local DEVELOPMENT (`EXECUTION_ID` `DVnnnn`, `RECORD_CLASS` DEVELOPMENT) needs the Playwright pin (`requirements.txt`, `--require-hashes`) and a hand-written `instance.json` for the SUT (the E03 README section 6 form). It never enters `raw-data/`. Local DRY_RUN is the same with `RECORD_CLASS` DRY_RUN.
3. Hosted DRY_RUN bundles are uploaded for review and never imported. The ORCHESTRATOR reviews them and records the findings (the E03 precedent).
4. The verification artifact (HD-22) is the run manifest, `actions.json` (per-action outcome, mechanism, and observation), and `precondition.json` (the starting-state check).
