## 1. Purpose

Unchanged from v1: this document defines the roles under which automated agents and humans operate this repository, what each role is responsible for, and where each role may and may not write, so that no result for any system under test (SUT) can be traced to a role that should not have produced it.

Nine agent roles now exist (EXECUTOR-E03-RESETABILITY, defined in v2 and v3 and never launched, is retired by this version; Section 3.5). Their names are exact and are used as-is in provenance records, prompts, and change-log entries:

ORCHESTRATOR; AUDITOR-SUT01-OMNIPIZZA; AUDITOR-SUT02-SAUCELABS; AUDITOR-SUT03-BROWSERSTACK; AUDITOR-SUT04-RESTFULBOOKER; AUDITOR-SUT05-JUICESHOP; AUDITOR-SUT06-WEBDRIVERIO; ADJUDICATOR-EU-01; QUALIFIER-MOBILE-01.

Humans are not agent roles. Humans approve freezes, decide escalations, and may direct any role; human edits remain subject to protocol/change-control-v1.md.

## 2. Common rules for all agents

Unchanged from v1 (rules 1–8), and apply to every role, including the ORCHESTRATOR when it coordinates the execution of E03-resetability (Section 3.5):

1. Read and follow the root AGENT-INSTRUCTIONS.md before acting.
2. Never invent evidence. Every claim must be backed by an evidence record with its evidence_id (evidence-rules-v1.md), or, for a run, by a run manifest (schemas/run-manifest.schema.json); unknown provenance is null / "null / TBD", never guessed.

4. Never change a file whose protocol state is FROZEN-PRE-DATA, AMENDED, or SUPERSEDED; never edit prompts/frozen/ or raw-data/ after the relevant freeze.
5. Record provenance for every artifact written: role name, prompt version id (once E03's prompt is frozen), date, protocol version in force.
6. Do not start any experimental campaign, audit, qualification run, or compatibility smoke unless explicitly instructed by the ORCHESTRATOR under human direction. At this document's creation (2026-10-26), E03-resetability is NOT_STARTED and no measured E03 run exists; the executions that other roles have performed on explicit human instructions — the Mobilewright qualification gate (2026-09-24, run 35938250936) and the two Appium 3 compatibility smokes (2026-09-27, run 36340774530; 2026-09-29, run 36539790536) by QUALIFIER-MOBILE-01, and the eight E03 environment-verification dispatches by the ORCHESTRATOR (2026-10-02, run 37074152972, to 2026-10-26, run 40361964609) — are tool-qualification and environment-verification records, not measured E03 runs (qualification/; manifests/toolchain-manifest.yaml; manifests/e03-environment-verification-run-v1.yaml and its successors).

### 2.1 Orchestration-review channel (new in v3)

The human research lead may give approvals and instructions to the study's independent orchestration reviewer, an external review function that is not a role of this document and holds no write authority over any tracked file. The reviewer relays them to the ORCHESTRATOR verbatim — the human's text, its timestamp, and its SHA-256 — inside a bounded operation instruction that states its scope and its exclusions. The ORCHESTRATOR records such an approval as given to the independent orchestration reviewer and relayed to the ORCHESTRATOR, never as live input to the ORCHESTRATOR, and records beside it any direct written confirmation the human gives to the ORCHESTRATOR (verbatim, or as a paraphrase with the SHA-256 of the exact text where publication hygiene keeps that text out of tracked files; AGENT-INSTRUCTIONS.md, "E03 CI/CD infrastructure"). The reviewer never approves anything itself: its drafts, proposals, and recommendations are never approvals, and a relayed text is an approval only if the human gave it as one. Read-only analysis and DRAFT preparation may run on the reviewer's bounded instructions alone. Every action that this document or AGENT-INSTRUCTIONS.md reserves to explicit human approval still requires the human's explicit approval of that exact action. The executing role may ask the human for a direct confirmation whenever the adoption of a relayed text is unclear (protocol/unresolved.md, PROTO-U10). Where the executing role's own operating rules require the human's direct written confirmation for a class of edits (for example the agent-instructions file), the human gives that confirmation directly to the ORCHESTRATOR and it is recorded beside the relayed approval; a standing written delegation by the human, recorded with the SHA-256 of its exact text, may cover a defined class of representation-only edits and is revocable by the human at any time. DRAFT preparation means creating or editing a file in state DRAFT (protocol/change-control-v1.md, section 2) or preparing a record that approves, freezes, authorizes, executes, dispatches, or publishes nothing.

### 3.5 E03-resetability execution under ORCHESTRATOR coordination (replaces the role EXECUTOR-E03-RESETABILITY; new in v4)

**Permitted campaign: E03-resetability only.** The role EXECUTOR-E03-RESETABILITY (new in v2, carried by v3) is retired by this version. It was never launched: no instruction was ever given to it and no measured E03 run exists (Section 2, rule 6). E03-resetability is executed under ORCHESTRATOR coordination, by the model of Section 3.6 and under the rules of this section; no agent session is instantiated per assigned SUT. This section grants no authority over E02, E04–E12 (Section 3.6 governs them) or any future campaign.

**Implementation and responsibility:** the executing program is the frozen E03 executor implementation (`experiments/E03-resetability/executor/`, entry point `run-condition.sh`, locked by its sha256 in the campaign configuration), run only by the frozen measured-execution workflow; it is a program, not an agent role, and takes no decision outside its code. On the ORCHESTRATOR's dispatch of one condition of one assigned SUT, one execution, one attempt (Dispatch, below), it executes the E03-resetability run for the conditions and canonical scenario(s) fixed in E03's locked campaign-configuration record (protocol/change-control-v1.md, section 7) and the FROZEN scenario mapping record(s) it cites (protocol/equivalent-scenario-mapping-v1.md; as of this revision, `experiments/scenario-mappings/CS-001.yaml`, FROZEN, the sole accepted canonical scenario for the current E03 campaign version — `experiments/scenario-mappings/CS-002.yaml` is EXCLUDED_FROM_CAMPAIGN since 2026-09-22, `manifests/e03-cs002-exclusion-v1.yaml`, and is never an input to the executor implementation) — never against a DRAFT configuration, a DRAFT mapping record, or an excluded mapping record. Concretely: establish the declared pre-reset (altered) state; perform the reset procedure under evaluation; independently verify pre-reset and post-reset state against the declared known initial state, counting that verification as a Required Action classified by its own mechanism (protocol/setup-effort-v2.md, section 5, rule 8 — human ruling A2); record the ordered Required Actions list (protocol/setup-effort-v2.md, section 4, action classes), including, per action, its SUCCESS / PARTIAL_SUCCESS / FAILURE outcome recorded separately from the count in the run manifest's `actions[].outcome` field (protocol/setup-effort-v2.md, section 5, rule 9 — human ruling B1; `schemas/run-manifest.schema.v2.json`, where the field is optional at schema level and mandatory on every emitted action record by E03 campaign convention; a retry is a further action record with `is_retry` true, never a change to an earlier action's outcome); write one run manifest per run conforming to `schemas/run-manifest.schema.v2.json`, with `reset_mechanisms` mandatory and non-empty, `agent_role` ORCHESTRATOR, and `prompt_version` the version id of the frozen E03 dispatch procedure (Section 5); record any manual intervention and its reason; record `environment_type` per run and never execute a deterministic-reset condition against a PUBLIC_HOSTED instance, nor any condition whose controlled instance is not recorded as verified `CONTROLLED` in the authoritative controlled-instance record for E03 (`experiments/E03-resetability/controlled-instance-determination.md`, or the successor record named by the locked campaign configuration; protocol/study-design-v1.md, section 10.3) — a condition recorded `NOT_EXECUTABLE_WITHOUT_CONTROLLED_INSTANCE` is never executed, and a provisioning or environment-verification record is never itself treated as execution authorization.

**Dispatch (Section 3.6, "Dispatch", as modified by this paragraph):** the ORCHESTRATOR dispatches `.github/workflows/e03-measured-execution.yml` only within a dispatch authorization that the human research lead issued, one per assigned SUT, naming that SUT's executable conditions and the number N of executions per condition; a dispatch authorization is not issued by this document, by a prepared record, or by a START, and the human may revoke it at any time. Within it the ORCHESTRATOR dispatches each execution in the order fixed by the locked campaign configuration without a further approval of each exact dispatch: it records the dispatch before it is made (condition id, execution id, attempt, inputs, UTC clock reading) and the run identity after the run starts (run id, run number, run attempt, head sha, creation time), makes exactly one dispatch per execution, never cancels, re-runs, or repeats a run, and never dispatches a second run of a condition while one is in progress. A further attempt is a new dispatch under its own explicit approval naming the condition and the execution, and a new run manifest with `attempt` incremented. The START of the campaign and the lock of its "Campaign configuration" record (protocol/change-control-v1.md, section 7, moment 1) are separately approved; no instruction launches an agent session for E03-resetability.

**GitHub Actions permissions (human decision, 2026-09-22: GitHub Actions is the E03-resetability CI/CD orchestrator; AGENT-INSTRUCTIONS.md, "E03 CI/CD infrastructure", `E03-CI-WRITE-AUTH-01`):** every E03 MEASURED_EXPERIMENT execution runs through the frozen GitHub Actions execution path under `.github/workflows/`; a local execution may only be DEVELOPMENT, SYNTAX_VALIDATION, TOOL_QUALIFICATION, SMOKE, ENVIRONMENT_VERIFICATION, or DRY_RUN and never enters the measured dataset. Within GitHub Actions the ORCHESTRATOR **may**: dispatch (`workflow_dispatch`) the already-authorized, version-pinned measured-execution workflow as the Dispatch paragraph states, supplying only the frozen inputs of the locked campaign configuration; read that run's own logs and artifacts; and import the run's immutable artifact bundle into `raw-data/E03-resetability/<assigned-SUT>/**` under hash verification (`experiments/E03-resetability/ci-cd-execution-model.md`). While the campaign is IN_PROGRESS the ORCHESTRATOR **does not**: edit a workflow definition, change GitHub repository settings, runner images, retry policy, concurrency policy, timeout, pinned runtime versions, or artifact-retention policy, or disable, reconfigure, or override a platform-level retry, timeout, or concurrency policy, except as a CI correction under `E03-CI-WRITE-AUTH-01` that has its own change-log row with the reason (protocol/change-control-v1.md, section 7, moment 1; results collected before the change are analyzed under the earlier configuration); it never merges a pull request that changes a pinned input, or approves its own changes beyond Section 3.1. If a platform-native re-run occurs, the GitHub run id and run attempt are mapped explicitly onto the study attempt lineage in the new attempt's run manifest, and the earlier attempt is left untouched.

**Attempt immutability (explicit):** the ORCHESTRATOR and the executor implementation never rewrite, replace, edit, or delete a previous attempt's run manifest or artifacts, under any circumstance, including a CI-native automatic retry — a further actual attempt is always a new run manifest with `attempt` incremented (schemas/run-manifest.schema.json), never a mutation of the prior one (the "Immutable output policy", below, generalizes to every attempt, not only the first).

**Isolation of measured jobs (explicit; the READ boundary of v3, carried):** a measured job of E03-resetability reads only the common frozen inputs (the authoritative frozen E03 campaign configuration — the locked "Campaign configuration" record; the accepted, frozen canonical scenario definition `experiments/scenario-mappings/CS-001.yaml`; the accepted, frozen mapping entry applicable to its assignment; the version-pinned workflow definition; the protocol documents in force, `schemas/run-manifest.schema.v2.json`, `manifests/sut-manifest.yaml`, `manifests/toolchain-manifest.yaml`, the provisioning and controlled-instance records for its own assigned SUT, and the frozen dispatch procedure), the artifacts, source, and configuration of its own assigned SUT where its condition requires them, and its own prior execution and attempt lineage under `raw-data/E03-resetability/<assigned-SUT>/**` where the frozen execution protocol requires it (for example to assign the next attempt number). It must not read, during campaign execution, the experimental measured outputs of any other SUT (`raw-data/E03-resetability/<other-SUT>/**`, any other SUT's run manifests, action records, artifacts, or environment-verification results produced as measured data), any derived or analysed E03 result, or any comparison across SUTs. In GitHub Actions this isolation is enforced structurally: the measured-execution workflow checks out only the common frozen inputs and the assigned SUT's own `raw-data/E03-resetability/<assigned-SUT>/` subtree, never another SUT's subtree, and no measured output of one SUT is an input to a measured job of another SUT. The ORCHESTRATOR's verification and import of archives is not part of any measured job (Section 3.6, "Isolation"). Cross-SUT measured-result contamination of a measured job is forbidden and is a boundary violation escalated under Section 6, regardless of whether the read changed anything.

**Write boundary (explicit):** `raw-data/E03-resetability/<assigned-SUT>/**` (layout per raw-data/README.md: one subdirectory per run, `run-manifest.json` plus raw outputs) is written only by the ORCHESTRATOR's import of a run's artifact bundle after it verified every downloaded archive against its GitHub digest (Section 3.6, "Import"); the measured job and the executor implementation write nothing to the repository. Non-measured records never enter `raw-data/` (raw-data/README.md, "Measured versus non-measured"). The ORCHESTRATOR writes nothing else concerning a run than its dispatch and run-identity records and the status records that AGENT-INSTRUCTIONS.md requires, and never edits an imported run output; a correction is a new derived record under `derived-data/` (raw-data/README.md, "Correction records").

**Immutable output policy (every attempt, not only the first):** once any attempt's raw observation directory is written under `raw-data/E03-resetability/<assigned-SUT>/<run-id>/`, it is never edited, renamed, or deleted (raw-data/README.md, rules 1–2), even by the ORCHESTRATOR, even to fix an error, and even when a CI platform's own native retry produced it; a correction is a new derived record under derived-data/ (ORCHESTRATOR-authored, raw-data/README.md, "Correction records"), never an edit here. Once the E03 campaign is frozen (protocol/change-control-v1.md, section 7), `raw-data/E03-resetability/` as a whole becomes append-only and a further run may be appended only with its own change-log row stating the reason.

**Execution without cross-SUT adaptation (new in v4):** the order of conditions and executions, the inputs of every dispatch, and the stop conditions are fixed by the locked campaign configuration and the frozen dispatch procedure before the first dispatch. No decision whether, when, or how to dispatch an execution depends on a measured output of any SUT. The ORCHESTRATOR follows the same procedure for every SUT, never compares, ranks, or references one SUT's outcome while executing, and states no preference between SUTs. It stops, without a further dispatch, only on the stop conditions of the frozen dispatch procedure (a failed gate job, a workflow conclusion other than success or a failure of the measured-execution job, a bundle without a run manifest, an input that differs from the locked configuration, a required crossing of a boundary of this section), and reports to the human research lead; a resumption needs the human's instruction.

**Disclosed difference from v3 (new in v4):** under v3 the executor session of an SUT could never read another SUT's measured outputs during the campaign, a separation that required separate agent sessions. Under this version the ORCHESTRATOR, one agent, verifies and imports the artifacts of every run and can therefore read the measured outputs of all SUTs while the campaign is IN_PROGRESS. This difference follows from the answer yes of the human research lead to OPEN-1 (2026-10-26) and is put to the human research lead at the freeze of this document, whose approval covers it. It is mitigated, not removed, by the structural isolation of measured jobs, the frozen executor implementation that takes no decision, the fixed dispatch plan of the paragraph above, the prohibition on analysis before the campaign freeze (the Cannot paragraph), and the recorded dispatch, run identity, and digest of every run. Any analysis or publication of E03 results states this limitation.

**Cannot (the ORCHESTRATOR, in the execution of E03-resetability):** invent evidence or fabricate a Required Actions count or a per-action outcome (Section 2, rule 2; the Implementation and responsibility paragraph); modify a SUT (Section 2, rule 3); edit, replace, or delete an imported run output (the Write boundary and the Immutable output policy); execute against a DRAFT campaign configuration, a DRAFT scenario mapping record, or an excluded mapping record (`CS-002.yaml`); execute a condition not recorded as verified `CONTROLLED` in the authoritative controlled-instance record (`experiments/E03-resetability/controlled-instance-determination.md` or its named successor); execute any MEASURED_EXPERIMENT outside the frozen GitHub Actions execution path; execute an Android Native or iOS Native condition before the mobile runner has passed the qualification gate and the assigned SUT has passed its own compatibility smoke (the mobile-runner policy in force, protocol/mobile-runner-policy-v3.md since 2026-10-02, sections 2 and 9; its predecessors v1 and v2 are AMENDED); rewrite, replace, or delete a previous attempt's output, including one produced by a CI-native retry; **adjudicate** — it never confirms, disputes, or resolves a capability score or an evidence conflict (that is ADJUDICATOR-EU-01's exclusive function, Section 3.3, scoped to E01 only in any case); **analyze hypotheses before the campaign freeze** — until E03-resetability is frozen (protocol/change-control-v1.md, section 7, moment 2) it computes, states, or implies no result for H1–H5, no comparison outcome, no effect size, and no confidence interval from E03 measured data (that analysis is ORCHESTRATOR/analysis/ work under protocol/statistical-analysis-plan-v1.md, after the campaign freeze); verifying the digest and the schema conformity of a bundle and counting imported runs per condition are not analysis; **start or freeze the campaign by itself** — whether E03 starts and whether it is frozen are ORCHESTRATOR-proposed, human-approved actions (protocol/change-control-v1.md, section 7); **modify protocol** other than through a new version file under change control.

**Relationship to the frozen dispatch procedure:** the ORCHESTRATOR's E03 dispatch procedure is written as `prompts/working/ORCHESTRATOR-E03-resetability-v1.md` and frozen at the E03 campaign START as `prompts/frozen/ORCHESTRATOR-E03-resetability-v1.md` (prompts/README.md, rule 2; Section 5), no later than the first run that uses it.
