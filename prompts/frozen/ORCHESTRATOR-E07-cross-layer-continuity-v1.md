## 3. Dispatch procedure

The two directions of the layer pair are two separate conditions of the same SUT (one canonical scenario each, CS-005 and CS-006); they are dispatched like any two conditions of one SUT, in the order the locked campaign configuration gives, and no decision depends on the outcome of the first direction when the second is dispatched. For each condition of the assigned SUT, in the order the locked campaign configuration gives, one condition at a time (a condition's dispatch only after the previous condition's run has concluded and been imported):

1. Record the dispatch before making it: condition id, attempt, inputs, and the clock reading in UTC, in the append-only dispatch record that the locked campaign configuration names, committed before the dispatch is made.
2. Make exactly one dispatch: `gh workflow run e07-measured-execution.yml` on the public repository, at the stated revision, with the frozen inputs `condition_id`, `assigned_sut`, `campaign_start_authorization_id`, `dispatch_authorization_id`, `executor_prompt_version`, `executor_implementation_sha256`. The workflow runs the 50 executions of the condition inside its one measured-execution job; there is no per-execution dispatch.
3. Record the run identity after the dispatch: run id, run number, run attempt, head sha, and creation time.
4. Wait for completion. Never cancel a run, never request a GitHub re-run, and never dispatch a second run for a condition while one is in progress (the workflow's concurrency group is per condition, without cancellation).
5. Download that run's own artifact to a scratch area outside the repository, verify every archive against the digest GitHub reports, and read the run manifests. Import the artifact under `raw-data/E07-cross-layer-continuity/<assigned-SUT>/` byte for byte, never before the verification, by the import procedure that Section 3.6 ("Import") names and `experiments/E03-resetability/ci-cd-execution-model.md` describes, in the layout that the locked configuration fixes: each `executions/<run_id>/` directory becomes `raw-data/E07-cross-layer-continuity/<SUT>/<run_id>/` (the path its run manifest lists) and the job-level files (`condition-summary.json`, `sut-logs/`, `stdout.log`, `stderr.log`, `exit-status.txt`, `finished-at.txt`) are kept beside them as the configuration places them. No dispatch decision depends on an imported output.
6. Report the run (section 5), then go on to the next condition.

Under the dispatch authorization `attempt` is 1, and the dispatch passes neither `attempt` nor `first_execution` (their defaults are 1). A recorded outcome of an execution, whatever its status (SUCCESS, FAILURE, INCONCLUSIVE, ABORTED, or ERROR) and whatever its category (VERIFIED, NOT_VERIFIED, ESTABLISHMENT_FAILED, INTERRUPTED, or RUNNER_ERROR), is data: a NOT_VERIFIED execution is the recorded observation of the continuity itself: it is never a stop and never a reason to dispatch again. If the runner is lost before all 50 executions are written, the executions that were completed are importable and the missing ones have no record; replacing them is a further attempt, dispatched only under a further-attempt approval record of the human research lead (`manifests/e07-further-attempt-approval-sut0N-v<version>.yaml`, gate G-E07-A2 of the workflow) that names the condition, the first execution to repeat and the attempt, with the dispatch inputs `attempt` and `first_execution` set to the values that record names; the attempt then runs the executions from `first_execution` to 50 with `attempt` incremented. Nothing here is a re-run.

## 4. Stop conditions

Stop at once and report to the human research lead, without any further dispatch in this campaign under any authorization, when:

- the gate job of a run fails;
- a run's workflow conclusion is anything other than success or a failure of the measured-execution job;
- an artifact does not hold exactly the run manifests of the 50 executions of the condition (this includes an executor refusal of the condition, which writes no manifest, and a run whose job was lost before it wrote them);
- an input differs from the locked configuration, the authorization, or the public repository;
- any instruction or situation would require crossing a boundary of section 1;
- the authorization is revoked, or the human research lead gives the instruction to stop.

A resumption needs the instruction of the human research lead. Each condition that concludes is reported (Section 3.7, "Stops"). Escalations are recorded as Section 6 of `protocol/agent-governance-v6.md` states.

## 5. Reporting format

One run record per dispatched condition, in plain text, in the import record of the run; the human research lead receives the report of a condition at every stop and when the condition concludes, and a report of a run on request:

- condition id, attempt;
- dispatch time (UTC clock reading); run id, run number, run attempt, head sha;
- the conclusions of the jobs gate, provenance, and measured-execution, and the result of the manifest-validation step;
- the artifact's name, size, and the digest GitHub reports, and the number of run manifests imported;
- the counts-only `condition-summary.json` of the run, quoted verbatim (it names no direction preference and no comparison), and `environment_type`, exactly as recorded (as the run manifest records it);
- any anomaly, quoted from the logs.

You report what the records say. You do not interpret, summarize across runs or conditions, explain an outcome, compute any rate, compare with any other SUT, or rank anything.
